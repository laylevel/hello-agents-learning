# 目前智能体的三种范式结构
## 1.ReAct机制，核心就是边思考边执行
## 2，Plan——Slove机制，先计划在执行
## 3.Reflection机制，先执行在反思
###  三者本质区别：
- ReAct机制：边思考边执行，适合动态和不确定的任务环境
- Plan——Slove机制：先计划在执行，适合步骤比较明确的任务
- Reflection机制：先执行在反思， 对已有结果进行评估，并根据反馈生成改进版本。
# ReAct机制的核心工作流程
用户输入问题
    ↓
Python 把问题、工具说明和历史记录放入提示词
    ↓
LLM 理解问题并决定下一步
    ↓
LLM 输出 Action，例如 Search["北京天气"]
    ↓
Python 解析 Action
    ↓
Python 找到并调用对应工具函数
    ↓
工具返回结果
    ↓
Python 把 Action 和 Observation 保存到 history
    ↓
Python 把 history 拼进下一轮提示词
    ↓
LLM 结合新结果继续判断
    ↓
输出下一个 Action 或 Finish
# Reflection机制的核心工作流程
- 先执行任务
- 再反思执行结果
- 再根据反思结果调整任务
- 再重复以上步骤，直到任务完成
## Reflection机制的实现
- 设计一个反思机制，主要负责根据大模型执行的结果和任务要求，生成反思结果
- 构建一个记忆管理系统，主要存放每一次大模型执行的结果以及反思机制给出的反思结果
- 用户输入目标，调用大语言模型，大语言模型给出执行结果，memory管理系统将执行结果存储起来，Reflection Agent 通常由外部 Python 代码 负责协调：先生成初始结果，将其保存到 Memory；再取出最新执行结果，通过提示词交给 LLM 进行反思；如果需要改进，就把反馈和当前结果再次交给 LLM 生成新版本，重复这一过程。Memory 只负责保存和读取记录，不会主动调用 LLM，也不会自动把记录传回模型。
## memory管理系统的设计(主要解决agent的上下文记忆问题)
- 初始化空列表，用于存储每一次大模型执行的结果以及反思机制给出的反思结果
- 设计一个函数，该函数主要负责把大语言模型执行的结果以及反思机制给出的反思结果加入memory管理系统当中（每次增加一条记录）
- 设计一个 def get_trajectory(self) 将所有记忆记录格式化为一个连贯的字符串文本，用于构建提示词，传给大语言模型
- 设计def get_last_execution(self) 获取最新一次的执行结果，将其交给大语言模型，用于下一轮的循环
## 反思可以从以下维度进行评估（相当于评审员）
- 事实性错误：是否存在与常识或已知事实相悖的内容？
- 逻辑漏洞：推理过程是否存在不连贯或矛盾之处？
- 效率问题：是否有更直接、更简洁的路径来完成任务？
- 遗漏信息：是否忽略了问题的某些关键约束或方面？ 根据评估，它会生成一段结构化的反馈 (Feedback)，指出具体的问题所在和改进建议。
## Reflection机制的成本
 1）主要成本
1. 模型调用开销增加:这是最直接的成本。每进行一轮迭代，至少需要额外调用两次大语言模型（一次用于反思，一次用于优化）。如果迭代多轮，API 调用成本和计算资源消耗将成倍增加。
2. 任务延迟显著提高:Reflection 是一个串行过程，每一轮的优化都必须等待上一轮的反思完成。这使得任务的总耗时显著延长，不适合对实时性要求高的场景。
3. 提示工程复杂度上升:如我们的案例所示，Reflection 的成功在很大程度上依赖于高质量、有针对性的提示词。为“执行”、“反思”、“优化”等不同阶段设计和调试有效的提示词，需要投入更多的开发精力。
（2）核心收益
1. 解决方案质量的跃迁:最大的收益在于，它能将一个“合格”的初始方案，迭代优化成一个“优秀”的最终方案。这种从功能正确到性能高效、从逻辑粗糙到逻辑严谨的提升，在很多关键任务中是至关重要的。
2. 鲁棒性与可靠性增强:通过内部的自我纠错循环，智能体能够发现并修复初始方案中可能存在的逻辑漏洞、事实性错误或边界情况处理不当等问题，从而大大提高了最终结果的可靠性。
